THE BIG IDEA
It is RAM with a built-in memory of its last safe state
UM002B combines two ways of representing the same bit. One is fast but forgetful. The other is slower to change but remembers without power.

The capacitor: the working desk
A capacitor stores a bit as electrical charge. It is quick to read and write, which is why the computer uses it during normal operation.
Charge leaks away. The controller must refresh it while power is on, and it disappears after power is lost.

The memristor: the locked notebook
A memristor stores a bit as a resistance state: an easier or harder path for current through a thin oxide layer.
It does not retain charge. Its physical resistance state can remain after power is removed.

The sentence to remember: the capacitor stores charge; the memristor stores resistance. The architecture translates the same digital 0 or 1 between those two physical forms.

Does stored data overload the CPU?
No. Data sitting in memory is not computation. A full bookshelf does not make the reader work harder; only opening and using a book does.
Refresh and backup sequencing are controller jobs, not application work for the CPU.

Where is the controller?
In the current design, the essential backup/restore controller sits on the same die, beside the memory array. It can react locally when power begins to fail.
A future module may add a higher-level controller to coordinate many dies, but each die still needs local rescue logic.

Important: "already in memory" does not mean "already running." Programs still need CPU time, initialization, decompression, security checks, and sometimes graphics preparation.

WHEN POWER BEGINS TO FAIL
The controller tries to create one complete, recoverable snapshot
A power-loss detector warns the on-die controller before the supply disappears completely. Reserve energy must keep the memory alive long enough to finish a controlled backup.

1
Freeze
Stop or drain normal memory traffic so the picture does not keep changing during backup.

2
Translate
Read each capacitor's 0 or 1 and program the matching memristor into a high- or low-resistance state.

3
Verify
Check rows and errorcorrection information before declaring the new snapshot complete.

4
Commit
Update protected metadata only after the snapshot is complete. This commit marker tells the next boot which version is safe to restore.

5
Power down
The capacitors may now discharge. The memristors retain resistance states without standby power.

If power disappears too early: the intended design restores the previous completed snapshot rather than mixing old and partly written rows. The most recent uncommitted changes may be lost, but a torn snapshot should not be presented as valid.
The prototype models include a short backup sequence for a very small demonstration array. A 20 GB, 200 GB, or other product-size device would require a new measured time and energy budget; the prototype timing must not be scaled by assumption.

What the user experiences
The machine can return to the last successfully captured memory image instead of rebuilding every byte from a separate storage device.

What this does not guarantee yet
"Instant-on" time for a full product has not been measured. Boot firmware, security, device initialization, and operating-system recovery may still add delay.

Core principle: the memristor does not keep charge trapped inside the capacitor. The capacitor is allowed to empty. Later, the retained resistance state tells the controller how to recharge it.

FILES AND CAPACITY
One pool can be shared, but the operating system must manage it
Imagine a 200 GB pool. If files and installed software occupy 100 GB, roughly 100 GB remains available for active work, subject to operatingsystem overhead and reserved space.

100 GB occupied

about 100 GB available

The boundary can move. Delete files and more space becomes available. Create files or install a game and less remains. Occupied bytes do not consume CPU time merely by existing.

When "Save" is pressed
The application and operating system update bytes and metadata in the pool. To make that update durable immediately, the system needs an explicit host-to-controller durability command or a completed snapshot.
A design that backs up only on power failure cannot honestly promise that every application "Save" has already reached the memristor.

When a file is deleted
The operating system marks its space reusable. The old bit pattern may remain physically present until overwritten, just as it can on conventional storage.
Secure deletion therefore needs a defined erase or cryptographic keydestruction policy.

Software matters: a truly unified memory-and-storage pool is not created by the cell alone. The operating system, file system, permissions, crash recovery, and durability rules must all understand the architecture.

The last completed memory snapshot may preserve the running state.

Recovery is limited by the snapshot contract; changes not committed before energy runs out can be lost.

The honest performance claim: this architecture aims to remove avoidable movement between storage and working memory. It does not make every application instant, and it does not make the processor or graphics card inherently faster.

How the CPU and GPU react
CPU: ideally sees a familiar memory interface. The on-die controller hides backup and restore. A larger software change is still needed if the same bytes are to behave both as files and as ordinary memory.

GPU: an integrated GPU could potentially share the pool. A discrete GPU normally keeps separate video memory, so one transfer stage can remain.

EVIDENCE AND NEXT PROOF
The architecture is coherent; product behavior still requires silicon

UM002B is presently a pre-silicon architecture supported by analytical models, simulation work, controller design, and prototype-scale planning. It is not yet a manufactured or qualified memory product.

Designed

The operating concept
Separate DRAM and non-volatile access paths, an on-die backup/restore controller, protected snapshot metadata, error correction, and power-fail sequencing.

Modeled

Key electrical and timing behaviors
Device and circuit models explore programming, leakage, thermal effects, disturb, and controller operation. Some modeled corners expose open risks rather than passing.

To prove

The product-level promises
Measured retention, endurance, full-capacity backup energy and time, restore time, yield, manufacturing rules, cost per bit, and real software performance.

Five questions a careful reader should ask
1. How much reserve energy is needed for the intended capacity at the worst temperature and voltage?
2. What is the exact durability rule for an application Save, not just for power failure? 3. How does the design recover when backup stops halfway through? 4. How long do measured resistance states remain readable after years without power? 5. What software changes are required to expose one safe pool for both files and working
